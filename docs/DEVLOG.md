## Day 1 (11/2): 환경 구축

### 계획 변경: Colab → 로컬 GPU
- 처음 계획서에는 GPU가 없다고 가정해 Google Colab을 쓰려고 했음.
- 집 PC에 **RTX 5080**이 있어 로컬(WSL2 Ubuntu)에서 전부 진행하기로 변경.
- RTX 5080은 최신 Blackwell 아키텍처(sm_120)라 **CUDA 12.8 이상으로 빌드된 PyTorch**(cu128)가 필요.
- 집 PC이므로 원칙을 정함: 작업 1회당 1시간 이내, 먼저 작은 샘플로 시간·온도를 재고 전체 실행, 밤샘 실행 금지.

### 시행착오 1: 가상환경이 만들어지지 않음
- 증상: `python3 -m venv .venv` → `ensurepip is not available`
- 원인: Ubuntu 시스템 Python 3.14에 pip·venv 패키지가 없음 (설치하려면 sudo 필요).
- 해결: **uv**(Rust로 만든 Python 패키지 관리자)를 사용자 홈에 설치하고 `uv venv --python 3.12`로 가상환경 생성.
- 배운 점: 연구용 라이브러리(torchreid 등)는 최신 Python(3.14) 지원이 늦음 → **한두 버전 낮은 Python(3.12)이 안전**.

### 시행착오 2: Windows PowerShell vs WSL Ubuntu
- 증상: 안내받은 명령을 실행했더니 `경로를 찾을 수 없습니다`
- 원인: 명령을 **Windows PowerShell**에서 실행함. 프로젝트는 WSL(Ubuntu) 안의 리눅스 파일시스템에 있음.
- 해결: PowerShell에서 `wsl ~` 입력 → 프롬프트가 `PS C:\...>`에서 `songmh135@user:~$`로 바뀌면 Ubuntu.
- 추가: 긴 명령을 붙여넣을 때 줄이 잘려 실행되는 문제 → `REPO=...`처럼 변수로 나눠 입력.

### 시행착오 3: torchreid 설치 (3단계 실패)
| 시도 | 결과 | 원인 / 대응 |
|---|---|---|
| PyPI `pip install torchreid` | 사용 안 함 | 원저자(KaiyangZhou)가 아닌 **제3자 재배포판**. 공급망 보안 위험 → 공식 GitHub 소스를 사용하기로 함 |
| 공식 GitHub 소스 설치 | `No module named 'tensorboard'` | 설치 스크립트가 버전을 읽으려고 패키지를 import → 의존성 tensorboard 등 선설치 |
| 재시도 | `command 'cc' failed` | C 컴파일러 없음 (Cython 확장 빌드) → `sudo apt install build-essential` |
| 재시도 | ✅ torchreid 1.4.0 | — |

- 배운 점: 패키지 이름이 같아도 **누가 배포했는지 확인**해야 함. 빌드가 필요한 패키지는 컴파일러 등 시스템 도구가 필요할 수 있음.
- 부수 문제: torchreid가 `opencv-python`을 설치하면서 기존 `opencv-python-headless`와 중복 → 하나로 정리 (같은 `cv2` 이름을 써서 충돌 가능).

### GitHub 연동
- `git push` → `could not read Username` (WSL에 GitHub 로그인 정보 없음)
- 해결: `sudo apt install gh` → `gh auth login`(브라우저 인증) → `gh auth setup-git`

## Day 1 (11/2): 데이터 확보와 저조도 합성

### 데이터
- Market-1501: Kaggle API로 다운로드 (146MB, 14초). 이미지 수가 표준과 일치하는지 확인: train 12,936 / query 3,368 / gallery 19,732.
- 실촬영은 생략 (일정·윤리 부담) → 공개 데이터셋에 저조도를 **합성**.
- DukeMTMC-reID는 원저자가 공개를 철회했으므로 사용하지 않음.

### 저조도 합성 설계 (`tools/synthesize_lowlight.py`)
단순히 픽셀값에 0.2를 곱하면 "어두운 사진"이 아니라 "어둡게 편집한 사진"이 됨. 실제 카메라에 가깝게 하려고 물리 기반 파이프라인을 사용:

1. sRGB → **선형(linear) 공간** 변환 (역감마). 빛의 양은 선형 공간에서 곱해야 물리적으로 맞음.
2. 약한 광학 블러
3. **노출 감소**: Low ×0.15~0.30, Extreme ×0.03~0.08
4. 색 틀어짐 (가로등 같은 따뜻한 색감)
5. **센서 노이즈**: Poisson(빛 입자 수의 무작위성, shot noise) + Gaussian(회로 노이즈, read noise)
6. 감마 복원 → 8bit → JPEG 압축 (CCTV 코덱 열화)

- **재현성**: 난수 시드를 (seed, 조도 등급, 파일 경로)로 정해 몇 번을 실행해도 같은 결과. 바이트 단위로 동일함을 확인.
- **메타데이터**: 이미지마다 실제 사용한 파라미터와 `mean_luminance`(평균 밝기)를 `synthesis_log.csv`에 기록.
- 결과: 36,036장 × 3등급, **13초** (CPU 8코어). 평균 밝기는 normal 0.396 / low 0.181 / extreme 0.081.
- 샘플 그리드: `docs/figures/lowlight_grid.jpg`

## Day 1 (11/2): 프로젝트 범위 재조정 (AI API 혼합안)

- 수업에서 AI API(Grok, GPT)를 지원받음 (반 공용 → 토큰을 아껴야 함).

- 검토 결과:
  - 핵심 실험은 원래부터 **학습이 아니라 사전학습 모델의 추론**이었음 → 로컬 GPU에서 몇 분이면 끝남, 비용 0.
  - ReID 자체를 비전 LLM으로 대체하면 query 3,368 × gallery 15,913 비교가 필요 → **수천만 회 호출**이라 비현실적이고, 표준 지표(Rank-1/mAP)와 비교할 수도 없음.
- 결정 (혼합안):
  - 직접 학습(Protocol B, 속성 분류기 학습)은 제외. OSNet·Zero-DCE·YOLO는 사전학습 가중치로 추론만.

- 토큰 절약 장치 (`vastreid/llm.py`): 응답 디스크 캐시, 실행당 호출 상한, dry-run(실제 호출 없이 횟수만 셈), 사용량 로그(`outputs/api_usage.csv`).
- 확인: Grok(`grok-4.20-0309-non-reasoning`), GPT(`gpt-4.1-mini`) 각각 1회 호출로 동작 확인.

## Day 1 (11/2): OSNet 베이스라인

### 평가 방법 (`tools/evaluate.py`, `vastreid/metrics.py`)
- 모델: OSNet x1.0, torchreid 공식 Model Zoo의 **Market-1501 학습 가중치** (학습하지 않고 그대로 사용).
- 지표: Rank-1/5/10, mAP, mINP. 표준 프로토콜대로 같은 사람이 같은 카메라에 찍힌 이미지는 정답에서 제외, junk 이미지(pid=-1) 제외.
- 지표 코드는 직접 작성하고, 손으로 계산한 작은 예제로 검증 (mAP 0.583, mINP 0.667 일치).
- 프로토콜:
  - **same**: query·gallery 모두 같은 조도
  - **cross**: query는 저조도, gallery는 normal → "밤에 찍힌 사람을 낮 기록에서 찾기" (실제 CCTV 상황)

### 시행착오 4: 샘플 결과만 보고 오해할 뻔함
- query 300장 샘플로 먼저 실행 → normal Rank-1 **86.7%** (공식 94.2%보다 낮음) → 코드 버그를 의심.
- query 전체(3,368장)로 다시 실행 → **94.5%** (공식 94.2%와 일치).
- 원인: 앞쪽 300장(일부 ID)만 써서 생긴 **표본 편향**. 샘플은 시간 측정용이지 성능 판단용이 아님.
- 배운 점: 공식 수치를 재현하는 것이 파이프라인 검증의 가장 확실한 방법.

### 결과 (`results/baseline.csv`)
| 프로토콜 | query | gallery | Rank-1 | mAP | mINP |
|---|---|---|---|---|---|
| same | normal | normal | 94.5 | 82.6 | 51.0 |
| same | low | low | 48.5 | 22.4 | 2.6 |
| cross | low | normal | 25.5 | 20.3 | 7.6 |
| same | extreme | extreme | 2.5 | 1.0 | 0.1 |
| cross | extreme | normal | 0.0 | 0.3 | 0.2 |

- Low에서 Rank-1이 거의 절반으로 떨어짐 → 프로젝트의 문제 제기를 수치로 확인.
- 야간 query → 주간 gallery(cross)가 같은 조도(same)보다 훨씬 어려움.
- Extreme은 무작위 수준 → 합성 강도가 너무 셀 수 있음 (보류, 이후 검토).
- 전체 평가 46초, GPU 최고 63°C.

## Day 1 (11/2): 저조도 개선 실험 1 — 전부 적용

- 비교: 적응형 감마, CLAHE, **Zero-DCE**(CVPR 2020, 공식 사전학습 가중치). 모든 query·gallery 이미지에 적용.
- Zero-DCE는 모델이 작아(파라미터 79,416개, 논문 값과 일치) 구조를 직접 정의하고 공식 가중치를 엄격 모드로 로드.

### 시행착오 5: GPU가 99%인데 작업이 끝나지 않음
- 증상: Zero-DCE 실행이 10분 넘게 진행되지 않음. `nvidia-smi`: 사용률 99%, 메모리 15.7/16GB, 전력은 64W로 낮음.
- 원인: 256장을 한 번에 넣어 VRAM이 가득 참 → Windows/WSL 드라이버가 일반 RAM을 대신 쓰는 **sysmem fallback**으로 극도로 느려짐.
- 해결: 32장씩 나눠 처리 → 256장에 0.34초, 최대 메모리 1.6GB.
- 배운 점: "GPU 사용률 높음 = 일을 잘하고 있음"이 아님. **메모리와 전력**도 같이 봐야 함.

### 결과 (`results/enhance.csv`) — 모두 성능 하락
| 개선 기법 | normal R1 | low/low R1 | low→normal R1 |
|---|---|---|---|
| 없음 | 94.5 | 48.5 | 25.5 |
| 감마 | 90.1 | 43.1 | 14.9 |
| CLAHE | 85.8 | 42.8 | 17.7 |
| Zero-DCE | 62.2 | 32.4 | 10.7 |

- 이미지로 원인 확인 (`docs/figures/enhance_grid.jpg`):
  1. 밝은 이미지까지 밝게 만들어 과노출·탈색
  2. 어두운 이미지를 밝히면 **노이즈도 함께 증폭**되어 컬러 반점 발생

## Day 1 (11/2): 저조도 개선 실험 2 — 게이팅·노이즈 제거

- 대응 ①: **밝기 게이팅**: 평균 밝기 < τ인 이미지에만 개선 적용.
  - τ=0.25는 **ReID 성능을 보지 않고** 합성 로그의 밝기 분포만 보고 정함 (normal 하위 5% = 0.257). 테스트 결과를 보고 τ를 고르면 결과를 부풀리는 것(data snooping)이기 때문.
  - 적용 비율: extreme 100%, low 약 92%, normal 약 4%.
- 대응 ②: **노이즈 제거 후 개선**: OpenCV Non-Local Means를 밝기 개선 전에 적용 (실제 카메라 ISP 순서).

### 결과 (`results/enhance_v2.csv`)
| 설정 (R1 %) | normal | low/low | low→normal | extreme |
|---|---|---|---|---|
| 없음 (기준) | 94.5 | **48.5** | **25.5** | 2.5 |
| 게이팅 + 감마 | 92.6 | 41.6 | 16.2 | 2.9 |
| 게이팅 + CLAHE | 93.6 | 42.2 | 16.7 | 3.5 |
| 게이팅 + Zero-DCE | 91.8 | 31.5 | 8.5 | 2.5 |
| 게이팅 + 노이즈 제거만 | 93.9 | 38.3 | 24.4 | 2.6 |
| 게이팅 + 노이즈 제거 + 감마 | 92.0 | 32.4 | 10.2 | 3.1 |
| 게이팅 + 노이즈 제거 + CLAHE | 93.0 | 42.3 | 23.4 | 3.1 |
| 게이팅 + 노이즈 제거 + Zero-DCE | 91.4 | 27.1 | 9.6 | 2.9 |

- 게이팅은 효과 있음: normal 손상 해결 (Zero-DCE normal 62.2 → 91.8).
- 하지만 저조도 이미지는 **어떤 조합도 기준을 넘지 못함**. 노이즈 제거만 해도 low/low 성능 하락 (질감 같은 세부 정보도 함께 지워짐).
- **결론 (부정적 결과)**: 픽셀을 밝게 만들어도 이미 잃은 정보는 돌아오지 않음. "저조도 개선 모델을 ReID 앞에 붙이면 된다"는 단순한 접근에는 한계가 있음.
- 다음 방향: 조도 변화에 비교적 강한 정보(옷 색, 가방 등 **속성**)를 활용한 재순위화.

## 배운 점 요약

1. **검증부터**: 새 파이프라인은 공식 수치 재현(94.5 vs 94.2)으로 먼저 검증하고 나서 실험한다.
2. **샘플은 시간 측정용**: 작은 샘플의 성능 수치로 결론 내리지 않는다 (86.7% → 실제 94.5%).
3. **부정적 결과도 결과**: 개선이 안 되는 이유를 이미지로 확인하고 원인을 설명할 수 있으면 의미 있는 발견이다.
4. **결과를 보고 파라미터를 고르지 않기**: 게이트 τ는 데이터 분포로만 정했다.
5. **환경 문제는 원인부터**: Python 버전, 실행 위치(Windows/WSL), 빌드 도구, 패키지 출처를 차례로 확인한다.
6. **자원 모니터링**: GPU 사용률만이 아니라 메모리·전력·온도를 함께 본다.

## Day 1 (11/2): 속성 라벨과 재순위화 (oracle 상한선)

### 속성 매핑 (`tools/build_annotations.py`)
- Market-1501_Attribute(Lin et al.)의 ID 단위 27개 속성 중 **의복·소지품 6개**만 사용: 상의 색, 하의 색, 소매, 하의 종류(바지/반바지/치마), 가방(백팩/핸드백/가방/없음), 모자.
- **제외**: gender, age, 그리고 성별을 간접적으로 드러낼 수 있는 hair. (연구 윤리 원칙)
- 색이 여러 개이거나 없으면 `unknown`으로 두고 비교에서 제외.
- 템플릿 캡션 생성 예: `흰 반팔 상의와 검은 반바지를 입고 가방을 든 사람`
- 검증: ID 0001의 캡션 "흰 반팔 상의와 흰 치마"가 실제 이미지(흰 원피스)와 일치함을 그리드로 확인.
- 출력: `annotations/person_attributes.json`(1,501명, 커밋), 이미지×조도별 어노테이션(108,108개, 45MB, 로컬 전용).

### 재순위화 (`tools/rerank.py`)
- `score = cos(f_q, f_g) + λ · (속성 일치 비율)`
- λ는 테스트셋이 아닌 **train 이미지로 만든 검증 분할**에서 고름.
- 첫 실험은 **oracle**: query·gallery 모두 정답 속성 사용 → "속성이 완벽하다면 얼마나 오를까"의 **상한선** (실제 시스템이 아님).

### 결과 (`results/rerank_oracle.csv`, 상한선)
| 프로토콜 | 조도 | cosine R1 / mAP | + oracle 속성 R1 / mAP |
|---|---|---|---|
| same | normal | 94.3 / 83.6 | 97.5 / 92.9 |
| same | low | 48.1 / 22.6 | 76.1 / 56.8 |
| cross | low→normal | 23.0 / 18.7 | 61.0 / 58.4 |
| same | extreme | 2.4 / 1.0 | 38.7 / 32.2 |
| cross | extreme→normal | 0.0 / 0.2 | 2.7 / 8.5 |

### 해석 시 주의 (시행착오 6)
1. **검증 분할의 편향**: normal 검증 mAP가 모든 λ에서 100%. OSNet이 바로 이 train 이미지로 학습되어 train 특징이 비정상적으로 좋기 때문. 그래서 train 기반 검증은 ReID 특징을 과대평가하고, λ를 실제보다 **작게** 고르는 쪽(보수적)으로 치우침. 대안이 마땅치 않아 이 한계를 명시하고 사용.
2. **oracle은 λ가 클수록 좋아짐**: 정답 속성은 틀리지 않으므로 λ가 검색 범위 끝(0.5)에서 선택됨. 사실상 "정답 속성으로 후보를 거르는" 효과라 실제 성능이 아닌 **상한선**으로만 해석해야 함.
- 의미: 저조도에서 무너진 외형 특징을 **신뢰할 수 있는 속성 정보**가 크게 보완할 수 있음 (low/low R1 48.1 → 76.1). 이제 관건은 "어두운 이미지에서 속성을 얼마나 정확히 예측할 수 있는가".
- 다음: 학습 없이 속성을 예측하는 방법(CLIP zero-shot, 비전 LLM 샘플)으로 현실적인 재순위화 성능 측정.

## Day 1 (11/2): CLIP zero-shot 속성 예측과 현실적인 재순위화

### CLIP 속성 예측 (`vastreid/clip_attr.py`, `tools/clip_attributes.py`)
- 모델: OpenCLIP ViT-B/16 (OpenAI 가중치), **학습 없이** 문장과 이미지의 유사도로 속성 예측 (zero-shot).
- 속성 값마다 문장 4개 템플릿을 평균 (예: "a surveillance camera photo of a pedestrian wearing a white shirt.").
- **시행착오 7**: CLIP 기본 전처리는 가운데를 정사각형으로 잘라냄 → 세로로 긴 사람 이미지는 머리(모자)와 발(하의)이 잘림. 여백을 채워 정사각형으로 만드는 letterbox 방식으로 변경.
- 전체 97,000장 예측 73초, GPU 최고 66°C.

### 속성 정확도 (%) (`results/attr_acc_clip.csv`)
| 조도 | 상의 색 | 하의 색 | 소매 | 하의 종류 | 가방 | 모자 | 평균 |
|---|---|---|---|---|---|---|---|
| normal | 46.8 | 25.5 | 88.7 | 69.5 | 34.1 | 52.0 | 52.8 |
| low | 48.5 | 27.1 | 85.0 | 63.2 | 27.6 | 25.9 | 46.2 |
| extreme | 32.3 | 26.2 | 50.5 | 29.6 | 14.9 | 3.3 | 26.1 |
| (참고) 가장 흔한 값만 찍기 | 30.5 | 40.7 | 94.0 | 55.1 | 40.3 | 96.9 | — |

- zero-shot CLIP은 상의 색·하의 종류 외에는 "가장 흔한 값만 찍기"보다 못함. 특히 모자는 모자를 안 쓴 사람(97%)에게도 "모자"라고 자주 답함.
- 조도가 낮아질수록 정확도 하락 (평균 52.8 → 46.2 → 26.1). 속성 인식도 저조도에 취약함.

### 재순위화 결과 (Rank-1 / mAP)
| 조건 | 외형만 (cosine) | + CLIP 속성 (자동) | + 목격자 속성 (witness) | + 정답 속성 (상한선) |
|---|---|---|---|---|
| normal | 94.3 / 83.6 | 94.3 / 83.6 | 94.3 / 83.8 | 97.5 / 92.9 |
| low/low | 48.1 / 22.6 | 49.1 / 23.7 | 48.8 / 23.4 | 76.1 / 56.8 |
| **low→normal** | 23.0 / 18.7 | **27.8 / 22.3** | **29.2 / 23.5** | 61.0 / 58.4 |
| extreme/extreme | 2.4 / 1.0 | 2.6 / 1.1 | 2.6 / 1.0 | 38.7 / 32.2 |

- witness: query 속성은 사람이 진술한 것으로 가정(정답으로 대체), gallery 속성은 CLIP 예측. 목격자 진술과 CCTV 기록을 함께 쓰는 실제 수사 시나리오.
- **처음으로 저조도 성능이 개선된 방법.** 특히 밤 query → 낮 gallery(low→normal)에서 Rank-1 +4.8~6.2%p. 유클리드 거리 베이스라인(25.5 / 20.3)과 비교해도 높음.
- 같은 조도끼리(low/low)는 +1%p 정도로 작음. extreme은 거의 변화 없음.
- 정답 속성(상한선)과의 격차가 큼 → **속성 예측 정확도를 높이면** 더 회복할 여지가 있음.
- 회귀 검사: 코드를 확률 기반으로 바꾼 뒤 oracle 결과가 이전과 바이트 단위로 동일함을 확인.

## Day 1 (11/2): 선형 분류기로 속성 예측 개선 (A)

- 결정: CLIP은 그대로 두고(학습 안 함), CLIP 이미지 특징 위에 **속성마다 로지스틱 회귀** 하나. train 속성 라벨만 사용하고, 세 조도의 train 이미지를 모두 써서 조도 변화에 강하게 함. 딥러닝 학습이 아닌 선형 모델 (`tools/attr_probe.py`).
- **정보 누출 방지 (시행착오 8 예방)**: λ 검증에 쓰는 train 이미지의 속성은 **그 사람 ID를 빼고 학습한 분류기**로 예측 (ID 기준 5-fold 교차 예측). 이미 본 이미지를 예측하면 속성이 거의 완벽해 보여 λ가 부풀려지기 때문.
- 소요: 5분 (CPU, 교차 예측 포함). 처음 예상한 "몇 초"보다 오래 걸림.

### 속성 정확도 (%) (`results/attr_acc_probe.csv`)
| 조도 | zero-shot CLIP 평균 | + 선형 분류기 평균 | 상의 색 | 하의 색 | 가방 |
|---|---|---|---|---|---|
| normal | 52.8 | **78.3** | 66.0 | 60.0 | 64.8 |
| low | 46.2 | **75.3** | 67.0 | 56.5 | 55.5 |
| extreme | 26.1 | **65.1** | 54.1 | 42.8 | 42.6 |

### 재순위화 (Rank-1 / mAP)
| 조건 | 외형만 | CLIP zero-shot | **선형 분류기** | 목격자 + zero-shot | **목격자 + 선형 분류기** | 상한선 |
|---|---|---|---|---|---|---|
| low/low | 48.1 / 22.6 | 49.1 / 23.7 | 48.8 / 23.9 | 48.8 / 23.4 | **49.7 / 25.2** | 76.1 / 56.8 |
| low→normal | 23.0 / 18.7 | 27.8 / 22.3 | **29.6 / 24.3** | 29.2 / 23.5 | **34.3 / 28.3** | 61.0 / 58.4 |
| extreme/extreme | 2.4 / 1.0 | 2.6 / 1.1 | 2.7 / 1.1 | 2.6 / 1.0 | 3.0 / 1.2 | 38.7 / 32.2 |

- 속성 예측이 정확해지자 재순위화 효과도 커짐: 밤 query → 낮 gallery에서 Rank-1 **23.0 → 29.6(자동) / 34.3(목격자 진술)**.
- low→normal에서 λ가 검색 범위 끝(0.5)에서 선택됨 → 범위를 넓히면 더 오를 수 있음 (다음에 검증 분할 기준으로 확인).

## Day 1 (11/2): 비전 LLM도 저조도에서 속성을 못 알아볼까? (B)

- 질문: "최신 비전 LLM은 어두운 이미지에서도 옷과 소지품을 알아볼 수 있을까?"
- 방법 (`tools/vlm_attributes.py`): 테스트 query에서 서로 다른 50명(시드 고정) × 3조도 = 150장. Grok(`grok-4.20-0309-non-reasoning`), GPT(`gpt-4.1-mini`)에 6개 속성을 JSON으로 질의. 성별·나이는 판단하지 말라고 명시. 같은 150장에서 CLIP zero-shot·선형 분류기와 비교.
- 토큰 관리: dry-run(호출 0회)으로 횟수 확인 → 18회 시험 호출로 토큰 측정(호출당 입력 225~446, 출력 약 45) → 전체 실행. 결과 캐시로 재실행 시 재호출 없음. 전체 사용량: 약 300회, 약 12만 토큰.
- "unknown" 답변은 오답으로 처리.

### 결과: 속성 평균 정확도 (%) (`results/attr_acc_vlm.csv`, 150장)
| 모델 | normal | low | extreme | extreme에서 "unknown" 답변 수 |
|---|---|---|---|---|
| Grok | **85.6** | 75.7 | 36.7 | 68 / 300 |
| GPT-4.1-mini | 83.2 | 69.9 | 32.5 | 89 / 300 |
| CLIP + 선형 분류기 | 78.5 | **78.6** | **63.8** | 0 |
| CLIP zero-shot | 52.4 | 44.5 | 21.2 | 0 |

- 밝을 때는 비전 LLM이 가장 정확 (Grok 85.6). 하지만 **조도가 낮아지면 급격히 무너짐** (extreme 36.7 / 32.5).
- extreme에서 LLM은 "모르겠다(unknown)"고 답하는 경우가 많음 (GPT 300개 답 중 89개). 정직한 행동이지만 정확도에는 불리.
- CLIP + 선형 분류기는 조도 변화에 가장 강함. 단, 이 분류기는 학습 데이터의 분포(예: 모자 안 씀 97%, 반팔 94%)를 배워서 "흔한 값"을 잘 맞히는 효과도 포함됨 → 모자·소매 정확도는 그대로 비교하면 안 됨.
- **결론**: 최신 비전 LLM도 저조도에서는 속성을 거의 못 알아봄. 저조도 문제는 ReID 모델만의 문제가 아님. 표본이 50명이라 수치의 오차 범위가 큼(속성 하나당 ±약 7~14%p).

## Day 1 (11/2): 데모에서 발견한 현상 — 저조도 query가 같은 이미지로 몰린다 (hubness)

### 발견 계기
- 데모를 직접 써 보니, 어떤 query는 normal과 low에서 검색 결과가 거의 같고, 어떤 query는 완전히 달라짐.

### 분석 1: 데모 샘플 24장
- normal과 low의 top-10이 3개 이상 겹치고 정답 1위를 유지한 경우는 **4장뿐**. 나머지 20장은 겹침 0~2개, 정답 순위 급락 (예: 1위 → 270위, 1위 → 3,852위).
- top-10 겹침과 원본 밝기·노출 배율의 상관은 **-0.05 / 0.05** → "더 어두울수록 결과가 바뀐다"는 가설은 틀림.

### 분석 2: 전체 query 3,368장의 top-10 분포
| query 조도 | top-10에 나온 서로 다른 gallery 이미지 | 자주 나온 상위 20장의 점유율 | distractor(사람 아님) 비율 |
|---|---|---|---|
| normal | 12,100 | 0.6% | 2.2% |
| low | 6,564 | **22.2%** | **29.1%** |
| extreme | **176** | **96.1%** | **44.3%** |

- low에서 이미지 한 장(`1333_c2s3_031607_02`)이 3,368개 query 중 **938개**의 top-10에 등장.
- 이렇게 많은 query의 이웃으로 반복 등장하는 데이터를 **hub**라 부르고, 고차원 검색에서 알려진 현상(**hubness**).

### 분석 3: hub 이미지를 직접 확인 (`docs/figures/hub_gallery.jpg`)
- 땡땡이 원피스, 체크 치마, 꽃무늬 등 **잔무늬가 촘촘한 옷**이 대부분.
- 해석: 저조도 이미지의 센서 노이즈(작은 점)를 모델이 **옷의 잔무늬로 착각**. 그래서 서로 다른 사람의 어두운 query가 같은 무늬 옷 이미지로 끌려감.
- Zero-DCE로 밝혔을 때 노이즈 반점이 커지며 성능이 더 떨어진 것과 같은 맥락.

### 배운 점
- 평균 지표(Rank-1, mAP)만 보면 "성능이 떨어졌다"까지만 알 수 있음. **직접 데모를 써 보고 개별 사례를 들여다봐야** 왜 떨어지는지 보임.
- 다음 실험: 학습 없이 hubness를 줄이는 방법(CSLS)으로 성능 회복 여부 확인.

## Day 1 (11/2): hubness 완화(CSLS)로 큰 폭의 회복

### 방법 (`tools/hubness.py`)
- `점수 = cos(q, g) − β · r_g + λ · 속성 일치도`
- `r_g`: gallery 이미지 g가 **어두운 이미지들 전반**과 얼마나 비슷한지 (참조 집합과의 유사도 상위 k개 평균). 두루 비슷하면 hub이므로 점수를 깎음.
- 참조 집합: query와 같은 조도의 **train 이미지** (라벨 사용 안 함, 테스트 query는 사용 안 함). 검증 시에는 같은 사람 이미지를 참조에서 제외해 테스트 조건과 맞춤.
- k, β, λ는 train 검증 분할에서만 선택. 이번에 λ 범위를 1.0까지 넓힘 (이전 실험에서 0.5 경계에서 선택됐기 때문).
- 실행 7분, GPU 최고 47°C. 첫 실행은 코드 검사(쓰지 않는 import) 단계에서 멈춰 다시 실행.

### 결과 (Rank-1 / mAP, `results/hubness.csv`)
| 방법 | Low → Low | Low → Normal | Extreme → Normal |
|---|---|---|---|
| 외형만 | 48.1 / 22.6 | 23.0 / 18.7 | 0.0 / 0.2 |
| + 예측 속성 | 48.8 / 23.9 | 31.6 / 25.4 | 0.0 / 0.4 |
| + 목격자 속성 | 49.7 / 25.2 | 34.3 / 28.3 | 1.7 / 3.0 |
| + CSLS | 50.7 / 25.5 | **43.1 / 33.8** | 0.4 / 0.6 |
| + CSLS + 예측 속성 | 52.2 / 26.9 | 49.2 / 38.2 | 1.3 / 1.3 |
| + CSLS + 목격자 속성 | **53.7 / 28.4** | **52.0 / 40.7** | **9.3 / 6.5** |

- **CSLS만으로 야간→주간 Rank-1이 23.0 → 43.1** (거의 2배). 지금까지 시도한 방법 중 가장 큰 효과.
- hub 점유율(상위 20장)도 22.2% → 3.9%로 감소 → 원인 분석이 맞았음을 수치로 확인.
- CSLS와 속성은 서로 다른 문제(hub 제거 / 정보 추가)를 다뤄 효과가 더해짐: **23.0 → 52.0**.
- Extreme→Normal도 0.0 → 9.3으로 처음 의미 있는 값이 나옴 (목격자 속성과 함께).
- Normal에서는 CSLS가 거의 영향 없음 (94.3 → 93.7). hub가 없는 곳에서는 할 일이 없기 때문.
- 주의: Low→Normal에서 β가 검색 범위 끝(1.0)에서 선택됨 → 범위를 넓히면 더 오를 수 있음.

### 배운 점
- **데모에서 눈으로 본 이상한 현상 → 원인 분석 → 원인에 맞는 해결책** 순서가 가장 큰 개선을 가져옴.
- 밝기를 올리는 방법(증상 치료)은 실패했고, 검색 단계에서 hub를 다루는 방법(원인 치료)은 성공.

### README 전면 개편

## Day 1 (11/2): 데모에 CSLS 추가, β 범위 확장, AdaBN으로 큰 폭의 회복

### 데모에 CSLS 옵션
- 이미지 검색 탭에 Hub 보정(CSLS) 체크박스와 β 슬라이더 추가. 샘플 #0(저조도)의 정답 순위: 270위 → **1위**.

### 시행착오 10: 하이퍼파라미터 탐색이 너무 느림
- β 범위를 넓히자 조합이 늘어나 20분 동안 조건 5개 중 2개만 끝남 → 중단.
- 원인: 평가 함수가 query 3,000여 개를 하나씩 반복 처리.
- 해결: GPU에서 한 번에 계산하는 벡터화 버전(`vastreid/metrics.py: evaluate_fast`) 작성. 기존 함수와 결과가 같고(최대 차이 3×10⁻⁸) **50배 빠름**(3.0초 → 0.06초). 전체 탐색이 20분 이상 → 13초.

### β 범위 확장 (`results/hubness_wide.csv`)
- 이전 실험에서 β가 탐색 범위 끝(1.0)에서 선택됨 → 범위를 0~3, k를 10/50/100, λ를 0~2로 확장.
- Low→Normal: β=1.25가 범위 안쪽에서 선택. CSLS 43.1 → **46.1**, CSLS + 목격자 속성 52.0 → **54.9**.

### AdaBN (`tools/adabn.py`, `results/adabn.csv`, `results/hubness_adabn.csv`)
- 아이디어: OSNet 내부의 BatchNorm은 밝은 사진의 평균·분산으로 특징을 정규화함. 어두운 사진엔 이 통계가 맞지 않아 특징이 쏠리고 hubness가 생김.
- 방법: **라벨 없는 저조도 train 이미지를 통과시켜 BN 통계만 다시 계산** (가중치 변경 없음, BN 80개, 8초). 저조도 query에는 저조도용 모델, 밝은 gallery에는 원래 모델 사용.
- 결과가 너무 커서 먼저 검증:
  1. normal 이미지로 통계를 다시 계산 → 94.2 / 82.3 (원래 94.5 / 82.6) → 정상
  2. 저조도용 통계를 밝은 query에 사용 → 41.5로 하락 → 조도에 맞춘 효과가 맞음
  3. 원본 모델 파라미터 변경 0개, 통계 재계산 전후 원본 출력 동일. 캐시 특징과의 0.2% 차이는 GPU TF32 연산 오차
- 결과 (Rank-1 / mAP, 코사인):

| 방법 | Low → Low | Low → Normal | Extreme → Extreme | Extreme → Normal |
|---|---|---|---|---|
| 외형만 | 48.1 / 22.6 | 23.0 / 18.7 | 2.4 / 1.0 | 0.0 / 0.2 |
| CSLS + 목격자 속성 | 53.7 / 28.4 | 54.9 / 42.2 | 3.5 / 1.5 | 8.9 / 6.4 |
| AdaBN | 80.7 / 60.0 | 85.3 / 71.0 | 17.2 / 7.8 | 25.4 / 19.8 |
| **AdaBN + CSLS + 목격자 속성** | **81.5 / 61.1** | **86.8 / 73.3** | **19.7 / 8.7** | **35.6 / 28.8** |

- AdaBN 후 hub 점유율이 0.6%(밝은 사진 수준)로 사라짐. CSLS는 검색 단계에서 증상을 다뤘고, AdaBN은 특징 단계에서 **원인**을 고친 것.
- AdaBN 위에서는 CSLS 효과가 작아짐(Low→Normal 85.3 → 85.1). hub가 이미 없어졌기 때문. 극저조도에서는 여전히 도움(25.4 → 28.5).
- 데모: AdaBN 옵션 추가. 샘플 #0 극저조도 query의 정답 순위 **2,548위 → 1위**. 벤치마크 탭에 방법별 종합 그래프 추가.

### 시행착오 11: 반올림 차이로 수치가 어긋남
- CSV에 소수 넷째 자리로 저장(0.8685)하자 데모 카드는 86.9, 실행 로그는 86.8(실제 0.86847)로 다르게 표시됨 → 저장 정밀도를 여섯째 자리로 늘려 일치시킴. 발표 자료와 데모 수치가 어긋나지 않도록 주의.

### 한계 (중요)
- 합성 저조도는 이미지 전체에 같은 방식으로 적용된 변화라 AdaBN과 특히 잘 맞음 → **실제 야간 영상에서는 효과가 작을 수 있음.** 발표에서 반드시 언급.

## Day 1 (11/2): MOT17 저조도 트래킹 평가

### 준비
- MOT17(Kaggle, 5.9GB) 중 train 시퀀스 3개만 압축 해제: 02(광장), 04(혼잡한 거리), 09(보행로), 총 2,175프레임. 검출기 이름(DPM/FRCNN/SDP)만 다르고 이미지는 같아 FRCNN 버전 사용.
- 같은 저조도 합성을 MOT 모드로 적용: 시퀀스마다 노출·색감을 고정해 프레임 간 밝기 깜빡임을 막고, 노이즈만 프레임마다 새로 생성. 1080p라 느려서(3.2프레임/초) 작업자를 16개로 늘림 → 3분 15초.
- 패키지: ultralytics(YOLO11m), boxmot 26(ByteTrack, BoT-SORT), TrackEval(공식 레포, 사용자가 직접 설치). PyPI의 `trackeval`은 원저자가 아닌 포크라 사용하지 않음.
- 설계: YOLO 검출은 조도·시퀀스별 한 번만 계산해 모든 트래커가 공유(트래커 차이만 비교). BoT-SORT의 외형 특징은 boxmot 기본 ReID 대신 **우리 OSNet / AdaBN OSNet**으로 직접 계산해 전달.

### 시행착오 12: 트래킹 파이프라인
- **boxmot 26 API 변경**: 외형 특징을 `update(dets, img, embs)`로 넘길 수 없음. 설치된 소스를 읽어 `Detections(geometry=Boxes(...), embeddings=...)` 구조체로 넘기는 방식임을 확인하고 수정.
- **GPU 메모리 부족**: YOLO에 프레임 경로 600개를 목록으로 넘기자 전체가 하나의 batch가 되어 33.7GB 요청 → 실패. 50프레임 샘플에서는 드러나지 않았음. 16장씩 나눠 검출하도록 수정. 배운 점: **샘플은 시간 측정뿐 아니라 규모가 커질 때 생기는 문제를 다 잡아주지 못함.**
- **패키지 버전 변화**: boxmot 설치로 OpenCV 5.0 → 4.11, pandas 3.1 → 2.3으로 바뀜. 기존 코드는 문제없이 동작.
- 전체 트래킹 9분, 평가 9초, GPU 최고 63°C.

### 결과 (`results/tracking.csv`)
| 조도 | 트래커 | HOTA | DetA | AssA | IDF1 | ID 전환 |
|---|---|---|---|---|---|---|
| Normal | ByteTrack | 45.9 | 40.4 | 52.5 | 55.4 | 96 |
| Normal | BoT-SORT + OSNet | 45.0 | 38.3 | 53.0 | 54.5 | 90 |
| Low | ByteTrack | 43.7 | 38.0 | 50.4 | 53.0 | 94 |
| Low | BoT-SORT + OSNet (AdaBN) | 43.8 | 36.2 | 53.2 | 52.7 | 89 |
| Extreme | ByteTrack | 15.5 | 7.7 | 31.2 | 12.1 | 43 |
| Extreme | BoT-SORT + OSNet | 16.5 | 7.2 | 37.9 | 12.5 | 40 |
| Extreme | BoT-SORT + OSNet (AdaBN) | 17.0 | 7.2 | 40.3 | 13.0 | 34 |

### 해석
- **Low에서 트래킹은 거의 유지** (HOTA 45.9 → 43.7). ReID가 절반으로 떨어진 것과 대조적. 트래킹은 프레임 간 위치·움직임(IoU, 칼만 필터)이 주된 단서이고, YOLO 검출이 Low에서는 버티기 때문.
- **Extreme에서는 검출이 병목** (DetA 40.4 → 7.7). 사람을 못 찾으면 트래커가 할 수 있는 일이 없음.
- 남은 검출끼리 연결하는 능력(AssA)은 외형 특징이 개선: 31.2 → 37.9 → **40.3(AdaBN)**, ID 전환 43 → 34. ReID에서 효과를 본 AdaBN이 트래킹 연결에도 도움.
- 밝을 때는 오히려 ByteTrack이 조금 나음 (외형 정보 없이 움직임만으로 충분, BoT-SORT의 기본 설정 차이도 있음).
- 다음 아이디어: 검출이 병목이므로 **YOLO에도 AdaBN**(평가에 쓰지 않는 다른 MOT17 시퀀스의 저조도 프레임으로 BN 통계 재추정) 시도 가능.

## Day 1 (11/2): k-reciprocal 재순위화와 데모 화면 조정

### 계기
- 데모에서 회색 긴팔 + 어두운 바지 차림(ID 0230)처럼 흔한 옷차림은 Low에서도 정답이 3·4·5·9위에 흩어져 Rank-1을 놓침. 사용자 질문: "더 안 되나?"

### k-reciprocal 재순위화 (`tools/kreciprocal.py`, `results/kreciprocal.csv`)
- 원리: "A의 이웃에 B가 있고 B의 이웃에도 A가 있으면 같은 사람일 가능성이 높다". ReID 표준 기법(Zhong et al., CVPR 2017), 학습 없음.
- 파라미터는 논문 표준값(k1=20, k2=6, λ=0.3)으로 고정 (테스트셋으로 조정하지 않음).
- 먼저 AdaBN 특징으로 빠르게 확인: Low→Normal 85.3 / 71.0 → 89.8 / 87.8.

### 시행착오 13: 계산 순서를 잘못 잡음
- 처음에는 CSLS로 쿼리-gallery 거리만 바꾼 뒤 k-reciprocal에 넣음 → 결과가 CSLS 단독과 **소수점까지 동일**. k-reciprocal은 쿼리-쿼리, gallery-gallery 거리도 함께 쓰는데, 한쪽 거리만 바뀌어 세 거리의 척도가 어긋나며 이웃 계산이 무력화된 것.
- **k-reciprocal을 원래 거리에 먼저 적용하고, 그 결과에 CSLS·속성을 더하는 순서**로 수정. β·λ는 새 거리 척도에 맞춰 검증 분할에서 다시 선택.
- 배운 점: 결과가 다른 방법과 "완전히 같다"면 효과가 없다는 뜻이 아니라 **코드가 실제로 그 방법을 실행하지 않았을 가능성**부터 의심할 것.

### 결과 (Rank-1 / mAP)
| 방법 | Low → Normal | Extreme → Normal |
|---|---|---|
| 외형만 | 23.0 / 18.7 | 0.0 / 0.2 |
| k-reciprocal만 (AdaBN 없음) | 19.9 / 22.2 | 0.0 / 0.2 |
| AdaBN | 85.3 / 71.0 | 25.4 / 19.8 |
| AdaBN + CSLS + 목격자 속성 | 86.8 / 73.3 | **35.6** / 28.8 |
| AdaBN + k-reciprocal | 89.8 / 87.8 | 30.2 / 32.5 |
| **AdaBN + k-reciprocal + CSLS + 목격자 속성** | **90.3 / 88.2** | 34.4 / **37.3** |

- **AdaBN이 먼저 hub를 없애야 k-reciprocal이 효과를 냄.** AdaBN 없이 쓰면 오염된 이웃을 강화해 오히려 하락(23.0 → 19.9).
- mAP가 특히 크게 오름(73.3 → 88.2): 정답 사진들이 위쪽으로 모임.
- 어려운 사례(ID 0230)는 그대로 어려움: Low 정답 첫 순위 3위 유지(AP 0.39 → 0.42). 흔한 옷차림은 외형 정보만으로 구분하기 어려움.

### 데모 반영
- 모델 선택에 재순위화 옵션 추가. k-reciprocal은 쿼리마다 계산하면 20초 이상 걸려 샘플 쿼리 24개 결과를 미리 계산(`tools/build_demo_cache.py`).
- 카드 점수는 보정 후 내부 점수 대신 **원래 코사인 유사도**를 표시 (CSLS 적용 시 0.18처럼 낮게 보여 헷갈렸음).

### 시행착오 14: 화면 크기 맞추기 — 여러 번 시도 후 롤백
- 요청: 넓은 화면(약 2000px)에서 공백이 많음 → 시도와 결과:
  1. 폭 제한을 풀고 카드 높이를 화면 높이에 맞춤 → 요소가 지나치게 늘어나 "더 이상해짐". 동시에 서버를 재시작하지 않아 화면(새 코드)과 서버(옛 코드)가 맞지 않아 결과가 비어 보임.
  2. 시안 크기(1440px)를 유지하고 전체를 같은 비율로 확대(zoom) → 비율 유지 OK.
  3. 카드 1:2 비율 + Top-10 한 줄 → "두 줄로" 요청.
  4. 두 줄 + 화면 높이 맞춤 + 가운데 정렬 → "오히려 망가짐" → **2번으로 롤백.**
- 이후 텍스트 검색의 오른쪽 "선택한 인물" 카드만 결과 영역 높이까지 늘리고, 선택한 인물 사진으로 빈 공간을 채움.
- 배운 점: 넓고 낮은 화면에서는 "두 줄 + 스크롤 없음 + 세로 카드 비율 + 좌우 공백 없음"을 동시에 만족할 수 없음. **한 번에 하나씩 바꾸고 확인받기**, 화면 코드를 바꾸면 **서버·브라우저 캐시를 같이 갱신**하기.

### 주의

### 시행착오 17: 목격자 진술을 넣으면 오히려 정답률이 무너짐
- 현상: 데모에서 속성(상의 색, 가방)을 입력하면 결과가 크게 나빠짐.
- 측정 (전체 쿼리 3,368개, 미세조정 + CSLS, Rank-1 / mAP):

| 목격자 진술 | 속성 없음 | 고정 λ=0.5 (기존 데모) | 검증 λ × n/6 (수정) |
|---|---|---|---|
| Low, 정답 2개 (상의·가방) | 88.0 / 70.4 | 75.8 / 53.4 | 88.7 / 71.3 |
| Low, 틀린 상의 색 1개 | 88.0 / 70.4 | **21.5 / 17.2** | 88.0 / 70.3 |
| Extreme, 정답 2개 | 65.1 / 47.9 | 53.7 / 34.6 | 66.6 / 49.3 |
| Extreme, 틀린 상의 색 1개 | 65.1 / 47.9 | **10.8 / 8.9** | 65.1 / 47.7 |

- 원인 1: 재순위화를 끈 경로에서 화면이 **고정값 λ=0.5**를 보냈음. 검증으로 고른 값(0.1~0.3)의 2~5배.
  외형 점수는 상위 후보끼리 0.01~0.05 차이인데 속성 점수가 0.5 × (0~1)로 더해져 외형을 압도함.
- 원인 2: 갤러리 쪽 속성은 사람이 아니라 **CLIP 분류기 예측**이라 상의 색 66%, 가방 65%만 맞음.
  진술이 맞아도 정답 인물의 사진이 다른 색으로 예측되면 순위가 밀림.
- 원인 3: 속성 점수를 입력한 속성끼리 평균함 → 2개만 넣으면 속성 하나가 점수의 절반을 차지. 틀린 진술 하나가 결과 전체를 뒤집음.
- 수정: ① CSLS 경로도 train 검증 분할에서 고른 k·β·λ를 서버가 직접 사용(`csls_params`) ② 속성 점수에 n/6을 곱해 속성 하나당 가중치를 일정하게 유지.
- 결과: 맞는 진술은 소폭 도움, 틀린 진술은 거의 영향 없음. 재순위화 경로는 원래 검증값을 써서 문제가 없었음.
- 배운 점: 실험 스크립트에서 검증한 하이퍼파라미터가 **데모 화면 코드에는 반영되지 않았음**. 실험과 데모가 같은 값을 쓰는지 확인할 것.
- 한계: 속성 예측 자체가 부정확해 목격자 진술의 효과는 작음(+0.5~1.5). 미세조정 Low에서는 검증이 λ=0을 골라 속성이 아예 반영되지 않음.

### 속성 예측 개선 (C) + 진술 반영 강도 선택 (B)
**C. 갤러리 속성 분류기를 미세조정 OSNet 특징으로** (`tools/attr_probe.py --src`)
- 특징 출처 3가지를 비교, **train 교차 예측 정확도로 선택**(테스트셋 아님): CLIP+미세조정 OSNet 결합 81.5 > OSNet 81.1.
- 속성 평균 정확도 (query+gallery 전체):

| 분류기 특징 | Normal | Low | Extreme |
|---|---|---|---|
| CLIP (기존) | 78.3 | 75.3 | 65.1 |
| **CLIP + 미세조정 OSNet** | **83.4** | **82.3** | **78.3** |

  Extreme 상의 색 54 → 77%. 미세조정 OSNet이 어두운 사진에서 색 정보를 더 잘 보존함.
- 하지만 검색 정답률(자동 λ)은 거의 같음: 미세조정 + CSLS + 속성 Extreme 68.8 → 70.3, 재순위화 포함 79.2 → 78.9.
  - 이유 1: 속성을 예측한 특징이 검색에 쓰는 특징과 같은 OSNet이라, 속성이 주는 정보가 외형 특징과 **겹침**.
  - 이유 2: 검증이 여전히 작은 λ(0.05~0.1)를 고름. 그런데 테스트셋에서는 λ=0.3이 더 좋았음(맞는 진술 6개 Extreme 70.3 → 73.1).
    검증용 train 이미지는 OSNet이 학습한 이미지라 외형 점수가 지나치게 정확해 보여, **속성이 필요 없다고 과소평가**됨 (README 한계와 같은 문제가 미세조정 후 더 심해짐).

**B. 진술 반영 강도 선택** (데모 "진술 반영 강도": 자동 / 강하게 λ=0.3 / 매우 강하게 λ=0.9)
- 전체 쿼리, 미세조정 + CSLS, Rank-1 / mAP:

| 진술 | 자동 | 강하게 | 매우 강하게 |
|---|---|---|---|
| Extreme, 맞는 6개 | 70.3 / 53.4 | **73.1 / 57.0** | 66.9 / 49.4 |
| Extreme, 맞는 2개 | 약 67 / 50 | 69.7 / 52.6 | 65.2 / 45.3 |
| Extreme, 틀린 상의 1개 | 66.3 / 48.9 | 64.8 / 47.5 | **49.6 / 34.3** |

- "강하게"는 맞는 진술이면 도움, 틀리면 소폭 손해. "매우 강하게"는 맞는 진술도 손해(속성 예측 오류가 외형을 덮음), 틀린 진술은 크게 무너짐 → 시연에서 위험성을 보여주는 용도.
- 데모: 미세조정 백본은 결합 분류기와 이에 맞춰 다시 고른 λ(`results/*_pft.csv`) 사용, 텍스트 검색도 결합 분류기 사용. 결과 상단에 속성 하나당 가중치 표시.

### 벤치마크 화면 갱신 (미세조정 반영)
- 사용자 지적: 벤치마크 화면이 미세조정 이전 기준인 부분이 있음 → 점검 결과 표는 최신, 나머지 3곳이 이전 기준이었음.
- 핵심 지표 카드: "제안 방법 효과"를 Low 기준에서 **Extreme 기준(0.0 → 78.9, +78.9%p)**으로 변경, Low 92.8 병기.
- 표 마지막 행: 데모와 같은 설정(결합 속성 분류기, `kreciprocal_ft_pft.csv`)으로 통일 → 92.8 / 78.9. README 최종 수치도 맞춤.
- 실패 원인 분포: "미세조정 + CSLS" 설정 추가 (`tools/failure_analysis.py`). Extreme 오답 2,405 → 1,175건, 사람이 아닌 이미지로 가는 비율 18.5 → 15.9%.
  미세조정 백본용 hub 빈도도 함께 저장되어 데모 오답 원인에 hub 항목이 다시 표시됨.
- 트래킹: BoT-SORT + 미세조정 OSNet 추가 (`tools/track_mot.py --trackers botsort-osnet-ft`, 3분 33초) → **개선 없음**
  (Extreme HOTA 16.5, AdaBN 17.0). 극저조도에서는 검출(DetA 약 7.7%)이 병목이라 외형 특징을 바꿔도 효과가 없음.
- 배운 점: 모델을 바꾸면 결과를 보여주는 **모든 화면·문서의 기준 설정**을 함께 점검할 것.

## Day 1 (11/2): 온라인 저조도 합성과 "처음 보는 저조도" 시험

### 계기
- "같은 샘플로만 학습시키기 불안하다": 기존 미세조정은 미리 만든 low·extreme 사진 1장씩을 12 에폭 동안 반복해서 봄 → 그 노이즈 자체를 외웠을 수 있음.
- 외부 데이터 확인: NightReID(실제 야간 1,500명)·MSMT17 모두 서명한 동의서를 이메일로 보내야 받을 수 있음 → 사용자 신청 대기.
  RandPerson(가상 인물)은 같은 Market 평가에는 효과가 작고 "합성 위에 합성"이라 제외.

### 온라인 저조도 합성 (`tools/finetune.py --online`)
- normal 원본만 읽고, 매번 configs/lowlight.yaml 범위에서 노출·노이즈·블러·색·JPEG를 새로 뽑아 합성 → 같은 저조도 사진이 두 번 나오지 않음.

### 결과 1: 기존 시험(같은 합성 방식) — 차이 거의 없음
| | Normal | Low → Normal | Extreme → Normal |
|---|---|---|---|

### 짝 일관성 + Triplet + PK 샘플링 (`tools/finetune.py --pair`)
- 계기: Extreme 오답의 71%가 "외형 손실"(어두운 사진에서 특징 자체가 약함). DEVLOG 개선 후보 1·2번을 함께 적용.
- 방법
  - 원본 1장에서 normal 1장 + 저조도 1장(low·extreme 반반, 매번 새로 합성)을 **같은 반전·같은 erasing**으로 만들어 짝으로 학습 → 두 사진의 차이는 조도뿐.
  - 손실 = 분류(라벨 스무딩) + batch-hard triplet(margin 0.3) + 짝 일관성(어두운 특징과 같은 사진 밝은 특징의 코사인 거리, 밝은 쪽은 stop-grad로 주간 성능 보호).
  - PK 샘플링: 배치당 16명 × 4장(짝 포함 128장). 에폭당 이미지 수를 기존 온라인 학습과 같게(136,576장) 맞춰 **같은 학습량의 기존 12 에폭 모델과 비교**. 설정값은 미리 고정.
- 시간: 1 에폭 샘플 119초·61°C 확인 후 본 학습 12 에폭 약 23분, 최고 63°C. Windows에서 처음 돌린 학습(멀티 프로세스 데이터 로딩 문제 없음).
- 결과 (Rank-1 / mAP)

| 시험 | 기존 12 에폭 | 기존 24 에폭(현재 최종) | 짝 + triplet 12 에폭 |
|---|---|---|---|
| Market Normal | 88.8 / 70.6 | 89.6 / 71.3 | **90.2 / 72.8** |
| Market Low → 주간 | 86.0 / 66.5 | 86.7 / 67.3 | **87.3 / 68.8** |
| Market Extreme → 주간 | 67.1 / 47.5 | **69.2 / 49.0** | 66.3 / 48.3 |
| 처음 보는 노이즈 / 색 조명 | 50.6 / 56.8 | **53.7 / 57.9** | 48.1 / 56.5 |
| MSMT17 Normal / Low / Extreme | 46.6 / 43.2 / 30.1 | 47.0 / 43.7 / 30.8 | **52.0 / 47.7 / 31.1** |
| 조합 Low (k-reciprocal + CSLS + 속성) | 90.7 / 85.5 | 90.8 / 85.6 | **91.6 / 87.6** |
| 조합 Extreme | 82.2 / 77.2 | **83.0** / 77.9 | 81.4 / **78.1** |

- 해석
  - **다른 데이터셋(MSMT17) 성능이 크게 오름**(밝은 사진 46.6 → 52.0). triplet이 "같은 사람끼리 가깝게"를 직접 학습해 카메라·장소가 바뀌어도 버티는 특징을 배운 것으로 보임. mAP는 모든 시험에서 상승.
  - Extreme Rank-1과 처음 보는 노이즈는 소폭 하락. 짝 학습에서는 학습 이미지의 절반이 normal이고 extreme은 1/4로, 기존(조도별 1/3)보다 극저조도를 덜 봄 → 다음 실험에서 짝의 어두운 쪽 extreme 비율을 올려 확인.
  - 한 가지 시험만 좋아진 게 아니어서 방향은 맞지만, 극저조도가 목표인 프로젝트라 데모 기본 모델은 아직 교체하지 않음.
- 기록: Windows PowerShell의 `*>` 리다이렉트는 UTF-16으로 저장되어 로그 읽기가 번거로움 → 이후 로그는 bash 리다이렉트(UTF-8) 사용.
